# Архитектура и подтверждённые API

## Источники документации

Проверены 9 ноября 2026 года:

- [События виджетов](https://docs.streamelements.com/overlays/custom-widget-events): `onWidgetLoad`, `detail.fieldData`, `onEventReceived`, слушатели `message`, `widget-button`, `kvstore:update`; Twitch chat data.
- [Custom Widget и SE_API](https://docs.streamelements.com/overlays/custom-widget): `SE_API.store.get(key)` возвращает Promise объекта; `store.set(key, object)` полностью заменяет объект, имеет **недокументированное возвращаемое значение** и отправляет обновление каждому Custom Widget аккаунта. Удаление ключей не поддерживается. Ключ — буквенно-цифровая строка.
- [Структура и пользовательские поля](https://docs.streamelements.com/overlays/widget-structure): `text`, `checkbox`, `number`, `colorpicker`, `dropdown`, `sound-input`, `button`; свойства `label`, `value`, `min`, `max`, `step`, `options`, `group`.

Использованы только эти публичные контракты. `SE_API.getOverlayStatus` описывает состояние оверлея, не начало Twitch-стрима; он не используется как детектор эфира. Не используются фиктивные методы watchtime и неподтверждённые Twitch live-события. Документация не устанавливает гарантии CAS, транзакций, блокировок, порядка доставки и максимального размера store payload — таких гарантий проект не заявляет.

## Формат чата

```js
{
  detail: {
    listener: 'message',
    event: {
      data: {
        nick: 'viewer',
        userId: '123456',
        displayName: 'Viewer',
        msgId: 'message-id',
        text: 'Привет!',
        tags: { 'user-id': '123456', 'display-name': 'Viewer', id: 'message-id' }
      }
    }
  }
}
```

`parseMessage` выбирает `userId`, затем `tags['user-id']`, иначе нормализованный `nick`. Отдельно берутся `displayName`, затем `tags['display-name']`. Ключ записи — `id:…` или `login:…`. При появлении ID запись по логину мигрирует вместе с очередью. При временном отсутствии ID ищется уже известный логин. Совпадение нового стабильного ID с переиспользованным чужим логином не объединяет две ID-записи. `msgId`/`tags.id` используются для ограниченного кеша дедупликации последних 5000 сообщений; без ID сообщения дедупликация невозможна. Кеш сообщений между перезапусками не сохраняется.

Текст сообщения не используется и не сохраняется. Строки ограничиваются по длине, управляющие символы удаляются. Представление использует исключительно `textContent`; шаблоны не вставляют HTML.

## Модули в одном файле

Вкладке JS не нужен загрузчик модулей. Один IIFE включает независимо тестируемые компоненты; в Node они экспортируются через CommonJS.

- `settings`: разрешённые ключи, дефолты, ограничение чисел, списки исключений, безопасные цвета.
- `Engine`: только данные, условные часы, `checkRewardEligibility(user, now)`, приём сообщений, сессия, очистка, очередь, snapshot/restore. Проверяет длительность с первого сообщения, число сообщений, свежесть активности, исключения и состояние награды.
- `Persistence`: серверный store, подтверждения, сериализация, read-before-write, локальный резерв, конфликт экземпляров.
- `Renderer`: статический DOM, текст, CSS-переменные, таймеры фаз, необязательное Audio.
- Слой событий: создание/остановка компонентов, интервалы, небольшой буфер сообщений при асинхронной загрузке (не больше 5000), тестовые кнопки.

Повторное исполнение скрипта удаляет старые обработчики, интервалы, Audio и таймеры анимации. Повторный `onWidgetLoad` обрабатывается последовательно и дожидается незавершённой записи предыдущего runtime. Ошибка анимации не блокирует следующие уведомления. Продвижение очереди основано на таймерах, поэтому отсутствие `animationend` не создаёт зависания.

## Очередь и награды

Сообщение и периодическая проверка помещают ключ в FIFO и `pending` Set. Повторная заявка исключена. По умолчанию очередь содержит до 50 ожидающих пользователей; текущая анимация уже из неё удалена. При переполнении пользователь остаётся в основном учёте и повторно проверяется после текущей анимации/на следующем интервале. Это не гарантирует показ всем при потоке, превышающем скорость анимаций.

Перед выдачей проверяется свежесть условий, поскольку очередь может ждать долго. Неактивный или исключённый пользователь снимается с очереди без награды; новое сообщение сможет поставить его снова. Флаг `rewarded` и `rewardedAt` ставятся при извлечении, snapshot записывается до начала показа. Это политика «не повторять начатую награду», а не гарантированная доставка визуального уведомления при аварийном закрытии.

Повторы по умолчанию запрещены. При включении нужен новый полный интервал от `rewardedAt` **и новое сообщение после предыдущей награды**; исходный счётчик не обнуляется, `firstSeenAt` остаётся исходным. Проверка недавней активности по-прежнему действует.

## Сохранение и конкуренция

Схема v1: `schemaVersion`, `sessionId`, `startedAt`, `lastActivityAt`, `resetToken`, `updatedAt`, `users`, `queue`. Конверт добавляет случайные `writerId` и `writeId`. Неизвестная более новая схема блокирует запись. Испорченные записи отбрасываются по одной; некорректный/истёкший снимок запускает новую сессию с предупреждением.

Запись объединяется dirty-флагом и интервалом 5–60 секунд. Для каждой операции создаётся полный snapshot. Внутри runtime допускается одна запись. Если прогресс изменился, пока шла запись, dirty остаётся для следующей. Принудительная фиксация награды дожидается уже начатой записи и записывает новое состояние.

Порядок серверной операции:

1. Получить текущий объект через `store.get` с тайм-аутом 5 секунд.
2. Сравнить `writeId` с последним прочитанным/подтверждённым объектом. Несовпадение останавливает writer.
3. Вызвать `store.set(key, fullSnapshot)`. Если он всё же вернул Promise, обработать rejection, но не считать resolve подтверждением.
4. Ожидать `kvstore:update` с `event.data.key === 'customWidget.' + key` и соответствующим `writeId`, максимум 5 секунд.
5. После подтверждения обновить base и локальную резервную копию.

Чужой `writerId` в событии текущего ключа немедленно останавливает запись и выдачу наград. **Это обнаружение конфликтов, не распределённая блокировка:** между шагами 1 и 3 возможна гонка. Поддерживается только один активный экземпляр на namespace. Даже режим резервирования не делает несколько экземпляров безопасными.

При ошибке/тайм-ауте SE_API runtime переходит на localStorage и выдаёт предупреждение, автоматических фоновых попыток перехватить сервер нет. Новый запуск снова пробует сервер; серверный снимок при доступности приоритетен. У локального резерва тот же ограниченный срок и валидатор. Недоступный localStorage оставляет только RAM с предупреждением. `pagehide` пытается сохранить, но не гарантирует завершение.

## Сессии и очистка

Создание runtime не является началом нового стрима. Действующий snapshot восстанавливает `sessionId`. Сброс вызывается новым `resetToken`, кнопкой или общей неактивностью чата (по умолчанию 6 часов). Учитываются только принятые неисключённые сообщения, включая сообщения новых зрителей сверх лимита.

Ненаграждённые записи удаляются после срока неактивности, кроме ожидающих в очереди. Награждённые остаются tombstone до конца действующей сессии: иначе очистка разрешила бы повторную награду. Их сообщения также продолжают учитываться. Лимит пользователей включает tombstone; при заполнении новые записи не создаются. Общий snapshot старше retention не восстанавливается. Каждый ключ хранит лишь текущий полный снимок, история не накапливается.

Точный эфиро-зависимый сброс требует внешней интеграции; сейчас его заменяют ручной маркер и общий тайм-аут. Сессия может продолжиться через два близко идущих эфира, если не сбросить её вручную.

## Изоляция тестов

Боевой ключ: `storageNamespace + 'Live'`; тестовый: `storageNamespace + 'Test'`. Тестовый режим игнорирует чат и создаёт синтетические сообщения только кнопкой. «Показать тестовую анимацию» работает через отдельную ограниченную очередь представления и не создаёт награду пользователя. Превью устанавливает собственный SE_API, часы и namespace `PreviewOnly`, работает локально и не вызывает StreamElements.

## Производительность и расширение

Проверка — один проход по ограниченному Map каждые 10–30 секунд; сообщение обрабатывается без сканирования всех пользователей при наличии ID. В DOM всегда одна плашка и восемь частиц. CSS анимирует transform/opacity без blur/backdrop-filter, внешних шрифтов и постоянных canvas-циклов. Градиенты/тени статичны. Режим reduced motion скрывает частицы. Звук останавливается при завершении показа.

Будущие уровни достижений следует добавлять отдельными правилами Engine и версиями схемы; анимации — реализациями Renderer; Twitch EventSub/Streamer.bot — адаптерами событий с явными гарантиями источника. Аватары, персональные звуки, лидерборд и более точное присутствие сейчас не реализованы. Это сохранит основной движок независимым от сети и браузера.

## Совместимое обновление JavaScript во время работы

Необязательный `AUTOUPDATE.js` загружает основной JS из публичного GitHub через fetch и Blob script. Это отдельный транспортный слой, не новый StreamElements API. Обработчики загрузчика стоят в capture-фазе: сохраняют `onWidgetLoad`, буферизуют чат/кнопки при замене и пропускают подтверждения store. `runtime.canUpdate`, `prepareUpdate` и `resumeAfterUpdate` определяют границу передачи управления. Замена ждёт пустой очереди и окончания текущего показа/паузы, приостанавливает новый pump и периодические проверки, завершает запись и передаёт snapshot в памяти. При инициализации новый runtime проверяет совпадение ключа и валидирует этот snapshot обычным restore. Маркер `CHAT_THANKS_API:1` ограничивает загрузку совместимыми вкладками; при несовместимых изменениях он должен меняться разработчиком. Загрузчик не обновляет сам себя, CSS/HTML/FIELDS. Подробнее: [Автообновление](AUTOUPDATE.md).
